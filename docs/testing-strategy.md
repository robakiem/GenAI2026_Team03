# Babki: тестова стратегія

Документ описує, що і як ми перевіряємо в Babki зараз (463 автотести + 9 E2E-сценаріїв). Промпт: [prompts/6.2_testing_strategy.md](../prompts/6.2_testing_strategy.md).

## 1. Межі (Scope)

### Що покриваємо автотестами

Порядок за ризиком: найдорожча помилка — неправильні гроші.

| Ризик | Що саме перевіряємо | Правила / історії |
|---|---|---|
| Розрахунок грошей | поділ порівну, сумами, відсотками; зайві копійки за порядком у поїздці; жодна частка не 0.00; баланси дають у сумі 0; перекази однакові за будь-якого порядку витрат; ≤ n−1 переказів; приклад «Карпати» до копійки. Крім прикладів, **тисячі згенерованих випадків** (властивості-інваріанти) | BR-02…BR-09, BR-23…BR-27; US-019, US-020-a/b, US-044, US-048 |
| Введення сум і полів | `0`, `-1.00`, `1000000`, `1.234`, `1,50`, `abc` відхиляються; межі довжин і сум; кожна схема з `shared` перевірена напряму | BR-01; US-004, US-016 |
| Бізнес-правила і стани | після першого «сплачено» та після закриття витрати не додаються й не змінюються; правка замінює ту саму витрату; відмова нічого не змінює (відкат транзакції); повтор із тим самим `clientRequestId` не створює дубль, навіть при п'яти паралельних запитах | BR-13, BR-14, BR-36, BR-44; CD-11 |
| Паралельність | правка витрати і перша відмітка одночасно: збережений список завжди збігається з витратами, запізніла правка отримує 409 | NFR-08, ADR-0006 |
| Доступ і приватність | чужа поїздка → 404 на кожному ендпоїнті; чужі `expenseId`/`memberId` через свою поїздку не працюють; сторінка друга показує лише його переказ, без чужих токенів і реквізитів; сесії (повтор після виходу, прострочена, зіпсовані cookie, `Secure` за HTTPS) | BR-39…BR-43, NFR-03, NFR-04, CD-09, CD-10 |
| Обробка помилок | **єдина точка**: лише `errors.ts` формує тіло помилки; жодного `catch` у роутах; ін'єкція збоїв БД на кожному ендпоїнті дає загальний 500 без stack, SQL, шляхів і тексту бібліотеки; збій логується на сервері; немає `X-Powered-By`; на екрані лише український текст за кодом, а не англійське `message` | contracts §3.2, NFR-11 |
| Контракт API | кожна відповідь збігається зі схемою `shared` **без зайвих полів**; кожен код помилки з каталогу дає свій статус | contracts §2–§3 |
| Цілісність БД | CHECK-обмеження, унікальні індекси, зовнішні ключі, каскадне видалення, `BigInt` для переказів | contracts §1.9 |
| Інтерфейс | форми (поля, повідомлення, «нічого не надіслано» при помилці), живий розрахунок часток, сторінки поїздки, переказів і друга, перенаправлення на вхід при 401, тема | BR-21, US-004, US-016…US-021, US-031, US-050 |
| Наскрізний сценарій | реєстрація → поїздка → друзі → 4 витрати → «хто кому платить» → реквізити → сторінка друга в «чистому» браузері → правка витрати змінює всі сторінки. Усе на ширині 360 px без горизонтального скролу | BR-26, BR-40, BR-41 |
| Архітектура | напрямок залежностей `routes → services → data`, `shared` без залежностей, жодних `float`/`toFixed` для грошей, жодних бізнес-правил у роутах, жодних захардкоджених українських текстів, жодних `eslint-disable` / `as any` | CLAUDE.md §3, §5 |

### Що свідомо перевіряємо вручну

| Що | Чому вручну |
|---|---|
| Візуальний стиль (кольори, хвилясті краї, квіти, шрифти, теми) | це смак; автотест не скаже, чи «гарно» |
| Копіювання у справжній буфер, відкриття посилання на реальному телефоні | потрібні справжні пристрій і браузерні дозволи |
| Завантаження шрифтів Google Fonts | зовнішній сервіс; без нього має працювати системний шрифт |

**Чек-лист перед демо** (5 хвилин, ширина 360 px; більшість кроків уже в E2E, вручну дивимося на вигляд):
1. Пройти сценарій «Карпати»: Макс → Оля 362.13, Ірина → Оля 1932.62, Андрій → Оля 1352.62.
2. Усі три теми: текст читається, нічого не накладається.
3. Посилання друга на справжньому телефоні, реквізити копіюються.
4. На кожному екрані немає горизонтального скролу.

### Що ще не тестуємо

- Позначки «сплачено / підтверджено» і закриття (EP-15…EP-20) ще не реалізовані. Тест гонки використовує допоміжну транзакцію за ADR-0006; коли з'явиться EP-15, її треба замінити справжнім викликом, а у `contract.http.test.ts` додати тригери для `NOT_THE_PAYER`, `NOT_THE_RECEIVER`, `INVALID_STATE`, `STALE_TRANSFER` (список «ще недосяжних» тоді стане порожнім).
- Доступність (axe), візуальні знімки, тести міграцій зі старих версій, навантаження: поки не потрібні для MVP.
- Повноцінні chaos-тести (вбивство процесів, збої мережі): немає сенсу для одного процесу з однією SQLite. Збої БД покриті ін'єкцією (див. «Обробка помилок»).

## 2. Рівні та інструменти

| Рівень | Інструмент | Що перевіряє | Де | Тестів |
|---|---|---|---|---|
| Unit і властивості | Vitest | чисті функції, схеми, валідація; seeded-генератор випадків для грошових інваріантів | `packages/shared/src/*.test.ts` | 130 |
| Сервіси + БД | Vitest + справжній SQLite-файл | правила, транзакції, заморожування, гонки, обмеження БД, відкат | `apps/api/src/services/*.test.ts`, `src/data/*.test.ts` | ≈100 |
| HTTP / API | Vitest + Supertest проти `createApp(...)` | маршрути, коди, контракт без зайвих полів, безпека, обробка помилок, архітектура | `apps/api/src/*.http.test.ts`, `error-handling`, `architecture`, `edge-cases` | ≈120 |
| Компоненти | Vitest + React Testing Library + jsdom | форми, сторінки, повідомлення; **мережа (`fetch`) єдине, що підмінено** | `apps/web/src/**/*.test.tsx` | 113 |
| E2E | Playwright, встановлений Chrome, 360 px | повний сценарій на реальних API і веб-застосунку з тимчасовою БД | `apps/e2e/tests/` | 9 |
| Статичні | `tsc --noEmit`, ESLint з типами, `--max-warnings=0` | типи між web/api/shared/e2e, заборонені патерни | `pnpm typecheck`, `pnpm lint` | — |

Покриття вимірює `@vitest/coverage-v8` (`pnpm test:coverage`), нижні пороги в `vitest.config.ts` кожного пакета валять збірку: statements/lines ≥ 95 % (shared 97 %), branches ≥ 85–90 %. Зараз: shared 99 %, api 99 %, web 98 %. Число саме по собі нічого не гарантує, тому окремо перевіряємо тести мутаціями (див. §4).

## 3. Організація та дані

- **Розміщення.** Тест лежить поруч із кодом: `split.ts` → `split.test.ts`. Наскрізні та міжшарові тести названі за темою (`security.http.test.ts`, `contract.http.test.ts`). E2E: `apps/e2e/tests/`.
- **Назви.** Назва тесту повторює назву сценарію Gherkin з `docs/requirements.md` або формулює правило (BR-xx).
- **Еталонні дані.** Приклад «Карпати» (contracts §1.10): `packages/shared/src/test/carpathians.ts` і `apps/api/src/test/carpathians.ts`. Для веб-тестів: `apps/web/src/test/render.tsx` (`fakeApi`, `renderAt`, `expectNothingSent`).
- **Ізоляція БД.** `createTestDb()` створює новий SQLite-файл у тимчасовій папці та застосовує всі міграції; кожен тест має порожню базу, `cleanup()` її видаляє. HTTP-тести реєструють кожен свій акаунт з унікальною поштою. E2E запускає API на **окремих портах (3101/5273) і з окремою тимчасовою БД**, тому запущений `pnpm dev` і його дані не чіпаються.
- **Ін'єкція збоїв.** `apps/api/src/test/faults.ts` (`brokenPrisma`, `overrideInTransaction`) ламає БД зсередини, не змінюючи код застосунку.
- **Що не використовуємо.** Робочу базу `babki.db`, мережу, поточний час (крім сесій), порядок запуску. Випадкові токени перевіряємо за властивостями, а не за значенням.

## 4. Правила роботи

1. **Тести від вимог, а не від коду.** Для нової історії спершу тести з Gherkin і контрактів, red, потім код, green.
2. **Перевірка тестів мутаціями.** Навмисно ламаємо одне правило і дивимося, що падає саме потрібний тест. На етапі 6 перевірено 16 поломок (гроші, доступ, сесії, обробка помилок, форма, E2E). Двічі тест спершу **не** падав і виявився слабким («нічого не надіслано» перевірялось раніше, ніж іде запит; сторінка друга не рахувала свої переказів). Тепер усі виявляються.
3. **Баг → спершу тест.** Знайдений помилково: відтворюємо тестом, потім лагодимо. Так знайдено: 500 замість 400 на завеликий запит, заголовок `X-Powered-By`.
4. **Ворота.** `pnpm check` (typecheck + lint + test + build) зелений перед push; перед демо додатково `pnpm test:coverage` і `pnpm test:e2e`. Червоний тест не вимикаємо й не підганяємо під код, поки не перевірили вимогу.
5. **Команди.** `pnpm test` (швидкі, без браузера), `pnpm test:coverage`, `pnpm test:e2e` (потрібен Chrome; `E2E_BROWSER=chromium` для вбудованого Chromium Playwright).
