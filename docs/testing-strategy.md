# Babki: тестова стратегія

Документ описує, що і як ми перевіряємо в Babki зараз (гілка `feature/expenses`, 153 автотести). Промпт: [prompts/6.2_testing_strategy.md](../prompts/6.2_testing_strategy.md).

## 1. Межі (Scope)

### Що покриваємо автотестами

Порядок за ризиком: найдорожча помилка — неправильні гроші.

| Ризик | Що саме перевіряємо | Правила / історії |
|---|---|---|
| Розрахунок грошей | поділ порівну, сумами, відсотками; зайві копійки за порядком у поїздці; частки завжди дають точну суму і жодна не 0.00; баланси дають у сумі 0; перекази однакові за будь-якого порядку витрат; взаємозалік; ≤ n−1 переказів; приклад «Карпати» до копійки | BR-02…BR-09, BR-23…BR-27; US-019, US-020-a, US-020-b, US-044, US-048 |
| Введення сум | `0`, `-1.00`, `1000000`, `1.234`, `1,50`, `abc` відхиляються; межі 0.01 і 999999.99 приймаються | BR-01; US-016 |
| Бізнес-правила і стани | після першого «сплачено» та після закриття витрати не додаються й не змінюються; правка замінює ту саму витрату; відмова нічого не змінює; повтор із тим самим `clientRequestId` не створює дубль | BR-13, BR-14, BR-36, BR-44; CD-11 |
| Доступ і приватність | чужа поїздка → 404; без сесії → 401; сторінка за посиланням показує лише свої суми; чужі суми, баланси й реквізити не потрапляють у відповідь; невідоме чи обрізане посилання → нейтральне 404 | BR-39…BR-43, NFR-03, NFR-04 |
| Контракт API | статус-коди, єдиний формат помилки, `details` з кодом поля, `params` з різницею сум, cookie сесії | contracts §2–§3 |

### Що свідомо перевіряємо вручну

| Що | Чому вручну |
|---|---|
| Візуальний стиль (кольори, хвилясті краї, квіти, шрифти) | це смак і дизайн; автотест не скаже, чи «гарно» |
| Верстка на 360 px без горизонтального скролу | без браузерних тестів (див. §2) це швидше перевірити очима в DevTools |
| Копіювання реквізитів і посилань | Clipboard API залежить від браузера й HTTPS; у Node його немає |
| Відкриття посилання друга на реальному телефоні | потрібні справжній пристрій і мережа |
| Завантаження шрифтів Google Fonts | зовнішній сервіс; без нього має працювати системний шрифт |

**Чек-лист перед демо** (5 хвилин, Chrome DevTools, ширина 360 px):
1. Реєстрація → «Створити поїздку» → додати 3 друзів.
2. Додати 4 витрати «Карпати» (одна — сумами, одна — відсотками з помилкою 33.33×3, щоб побачити різницю 0.01).
3. «Хто кому платить»: Макс → Оля 362.13, Ірина → Оля 1932.62, Андрій → Оля 1352.62.
4. Ввести реквізити Олі, відкрити посилання Макса в анонімному вікні, скопіювати реквізити.
5. Обрізати посилання на 1 символ → «Посилання не знайдено» без назви поїздки.
6. На кожному екрані немає горизонтального скролу.

### Що ще не тестуємо

- Позначки «сплачено / підтверджено» і закриття (EP-15…EP-17, EP-19, EP-20): ще не реалізовані, тести напишемо першими разом із ними. Тоді ж додамо тест з ADR-0006: правка витрати і перша позначка паралельно → рівно одна отримує 409.
- Автотестів інтерфейсу немає (див. §2).

## 2. Рівні та інструменти

| Рівень | Інструмент | Що перевіряє | Де | Тестів |
|---|---|---|---|---|
| Unit | Vitest | чисті функції: `splitExpense`, `computeBalances`, `proposeTransfers`, `memberBreakdown`, `parseAmount`, перетворення помилок Zod | `packages/shared/src/*.test.ts`, `apps/api/src/validation.test.ts` та ін. | 77 |
| Сервіси + БД | Vitest + справжній SQLite-файл | бізнес-правила, транзакції, заморожування, 404 для чужих даних, приватність сторінки друга | `apps/api/src/services/*.service.test.ts` | 50 |
| HTTP / API | Vitest + Supertest проти `createApp(...)` | маршрути, коди, формат помилок, валідація тіла, cookie, 401 | `apps/api/src/*.http.test.ts`, `app.test.ts` | 26 |
| Статичні | `tsc --noEmit`, ESLint з типами, `--max-warnings=0` | типи між web/api/shared, заборонені патерни | `pnpm typecheck`, `pnpm lint` | — |

Найбільше тестів на рівні unit, бо вся логіка грошей — чисті функції в `packages/shared` (ADR-0006). Їх використовують і API, і форма, тому один тест покриває обидва боки.

**Чому поки без компонентних і E2E-тестів.** У `apps/web` немає власної логіки розрахунку: форма викликає ті самі функції з `shared`, які вже покриті. Для тестів компонентів потрібні `@testing-library/react` і `jsdom`, для E2E — Playwright. Це нові залежності, а за `CLAUDE.md` §6 їх додає команда. Пропозиція: додати Playwright, коли з'являться позначки оплати, бо там сценарій іде через двох людей (Координатор і друг за посиланням).

## 3. Організація та дані

- **Розміщення.** Тест лежить поруч із кодом: `split.ts` → `split.test.ts`, `expense.service.ts` → `expense.service.test.ts`. HTTP-тести одного епіку — `apps/api/src/<епік>.http.test.ts`.
- **Назви.** Назва тесту повторює назву сценарію Gherkin з `docs/requirements.md` («Leftover kopecks go to the earliest members», «Iryna sees only her own transfer»). Так по `pnpm test` видно, які критерії приймання виконані.
- **Еталонні дані.** Приклад «Карпати» (contracts §1.10) лежить в одному місці для кожного рівня: `packages/shared/src/test/carpathians.ts` (суми в копійках) і `apps/api/src/test/carpathians.ts` (`createTrip`, `addCarpathiansExpenses`, `startSettlement`).
- **Ізоляція БД.** `createTestDb()` (`apps/api/src/test/db.ts`) створює новий SQLite-файл у тимчасовій папці ОС і застосовує всі міграції з `prisma/migrations/` по порядку. Сервісні тести роблять це в `beforeEach`: кожен тест має порожню базу. HTTP-тести — у `beforeAll` на файл, а кожен тест реєструє свій акаунт з унікальною поштою, тому тести не бачать даних один одного. `cleanup()` відключає Prisma і видаляє файл.
- **Що не використовуємо.** Робочу базу `apps/api/prisma/babki.db` тести не відкривають. Тести не залежать від порядку запуску, поточного часу й мережі. Випадкові токени перевіряємо за властивостями (довжина, унікальність), а не за значенням.

## 4. Правила роботи

1. **Тести від вимог, а не від коду.** Для нової історії спершу пишемо тести з її Gherkin-сценаріїв і контрактів, запускаємо і бачимо, що вони падають (red). Лише потім пишемо код (green). Так помилка в коді не стає «нормою» в тесті.
2. **Перевірка тестів мутаціями** для логіки грошей: навмисно ламаємо одне правило (наприклад, копійки за порядком вибору) і переконуємося, що падає саме потрібний сценарій. Результат для зрізу 2: [6.1_RESULT.md](../prompts/prompts%20results/6.1_RESULT.md).
3. **Баг → спершу тест.** Знайшли помилку вручну — додаємо тест, який її відтворює, потім виправляємо.
4. **Ворота.** `pnpm check` (typecheck + lint + test + build) має бути зеленим перед push і перед PR. Червоний тест не вимикаємо і не переписуємо під код, поки не перевірили вимогу.
