# Prompt 6.3: Test coverage audit, smoke check and bug hunt

<role>
You are a sceptical QA engineer reviewing tests that another AI wrote. Your job is to find what the tests do NOT prove, not to praise them. Follow CLAUDE.md (contracts win, no new dependencies, minimal changes).
</role>

<task>
1. Coverage map. For every story in docs/requirements.md that is implemented (US-004, US-005, US-016…US-021, US-031, US-044, US-048, US-009, US-030, US-050), list each Gherkin scenario and the test(s) that check it (file + test name). Mark a scenario "not covered" or "covered only at service level" honestly.
2. Test quality. Read every *.test.ts and flag:
   - mocks or stubs where a real call is cheap (we have a real SQLite per test — a mocked Prisma or service is a smell);
   - assertions that can never fail or prove nothing: `toBeDefined`, `toBeTruthy`, `not.toContain(X)` where X could not be there anyway, `expect([a, b]).toContain(x)` that accepts either answer, checks of the status code without the body;
   - tests whose name repeats a scenario but whose data do not match it;
   - places where the expected value was copied from the code's output instead of computed from the requirement.
   For each finding: file:line, why it is weak, a concrete stronger assertion.
3. Bug hunt in what the tests cannot see. Focus on apps/web (no component tests exist): Tailwind class conflicts, form validation order (are all field errors shown at once?), query invalidation after each mutation, layout at 360 px with long names and 999999.99 amounts.
4. Smoke checklist. Write a checklist of at most 20 steps that covers the user path end to end (sign-up → trip → members → 4 Carpathians expenses → form errors → who pays whom → payment details → friend's link → edit → sign-out/sign-in) plus "no horizontal scroll at 360 px" on every screen. Give the expected result for every step.
5. Bugs. For each real bug: steps to reproduce, expected vs actual, root cause in the code. Do not fix anything until I confirm the list.
</task>

<rules>
- A finding needs evidence: a line of code, a failing run, or a screenshot. No "might be".
- Do not count a test as coverage just because its name matches a scenario: check its data and assertions.
- Do not propose new dependencies (Testing Library, Playwright in the repo): CLAUDE.md §6. Note where they would help.
- When a fix is approved: first a test that fails on the bug (where a unit test is possible), then the fix, then `pnpm check`.
</rules>

<output>
Markdown, in this order: coverage table; weak tests (table); bugs (numbered); smoke checklist; open questions.
</output>
