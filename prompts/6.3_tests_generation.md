## Goal
Write and wire up automated tests for the key user stories already implemented (create a trip,
expenses with the three split modes, "who pays whom", the friend's personal page, payment
details), derived from the Gherkin scenarios in docs/requirements.md and the rules in
docs/requirements-digest.md and docs/technical-contracts.md. Not from reading the code first:
when code and contract disagree, the contract wins and you report the mismatch.

## What to cover
1. Every story: the happy path AND the edge cases / forbidden actions / validation errors
   (boundaries: 0.01 and 999999.99, 1,50, 1.234, abc, empty, over-long names, 21st member,
   duplicate names ignoring case, freeze after first payment mark, closed ledger).
2. Money logic with property-style tests: a seeded PRNG (no new dependency), hundreds of generated
   cases, invariants (shares sum to the amount, no 0.00 share, balances sum to 0, <= n-1
   transfers, result independent of expense order). Failure messages must include the seed.
3. Security and privacy over HTTP: tenant isolation on EVERY endpoint (404 not 403), foreign ids
   used through my own ledger, the member page leaks nothing of other members (assert exact
   contents, not just absence of one string), sessions (replay after sign-out, expired, garbage
   cookies), hostile text stored literally.
4. Error handling: prove there is ONE place that turns failures into responses (static checks
   on the source) and that no stack trace, SQL, file path or library message ever reaches the
   client: inject failures into the database on every endpoint (Error, string, null, object with
   status/message) and assert a generic 500 in the documented error format, logged server-side.
   Check response headers (no X-Powered-By). On the web side assert the UI shows only the
   Ukrainian text mapped from error.code, never the developer message.
5. Contract tests: every success body parsed by the shared Zod schema AND equal to its parsed
   value (so extra fields fail); every code in ERROR_STATUS triggered or explicitly listed as
   "not reachable yet", with the status from the catalogue.
6. Database: CHECK constraints, unique indexes, foreign keys, cascades, BigInt round trip.
7. Concurrency: double submit with the same clientRequestId (all requests answered, one row),
   parallel member inserts, and an expense edit racing the first "reported paid". EP-15..20 may
   not exist yet; in that case simulate the mark with the transaction ADR-0006 prescribes, say
   so in a comment, and do not invent endpoints. Remember that "edit then mark" and "mark then
   refused edit" are both valid orders: assert consistency of the saved list, not "exactly one
   succeeds".
8. Components (React Testing Library + jsdom): forms, live share preview, messages, "nothing was
   sent" on invalid input (assert after a short pause, otherwise it passes vacuously), redirect
   on 401, neutral link-not-found page. Replace ONLY the network (fetch); everything else is real.
9. One end-to-end Playwright scenario at 360 px (installed Chrome via channel, no browser
   download) on separate ports and a throwaway database, so a running `pnpm dev` is never
   touched: sign-up, trip, friends, the four Carpathians expenses, the settlement to the kopeck,
   the friend page in a fresh browser context, truncated link, signed-out redirects, an edit that
   changes every page, and no horizontal scroll on each screen.
10. Architecture checks as tests: dependency direction, no floats for money, no business rules
    in routes, no hard-coded Ukrainian text outside i18n, no eslint-disable / as any.

## Rules for the tests themselves
- Test names repeat the Gherkin scenario name or state the BR/NFR rule.
- Use the "Carpathians" data as the reference example; isolate data with a fresh SQLite file per

- No mocks of my own code. No assertions that only restate the implementation. No weakened
  conditions to make a test pass: if a test fails, decide whether the test or the code is wrong,
  and say which.
- If you find a real bug, add the failing test first, then fix the code minimally, without
  inventing error codes, endpoints or UI texts (CLAUDE.md §6), and list every such fix.
