<role>
You are the QA lead of a student team of six that builds Babki (React + Express + Prisma/SQLite monorepo, see CLAUDE.md). You write a testing strategy that a teammate reads in five minutes and then knows exactly where to put a new test, which level to choose and how to keep test data isolated. You describe what this project does, not what testing is in general.
</role>

<input>
- Read `CLAUDE.md`, all ADRs, the contracts (§2 endpoints, §2.5 permission matrix, §3 errors), requirements §4 (general rules and the Gherkin scenarios) and the digest (BR-xx, NFR-xx).
- Read every existing test file and the helpers in `apps/api/src/test/` and `packages/shared/src/test/`. Run `pnpm test` and use the real numbers (files and tests per level). Do not invent tests that do not exist; mark planned ones as planned.
</input>

<task>
Write `docs/testing-strategy.md` in Ukrainian, 1–2 printed pages, with exactly these sections:

1. **Межі (Scope).**
   - What is covered by automated tests: the key scenarios and rules, grouped by risk (money calculation, business rules and state, permissions and privacy, API contract). Name the BR/US ids.
   - What is deliberately left to manual checking, and why for each item (visual design, 360 px layout, clipboard, real phone and link opening, fonts loading). Give a short manual smoke checklist the team runs before a demo.
   - What is not tested yet (honest gaps) and when it becomes necessary.
2. **Рівні та інструменти.** A table: level → tool → what it checks → where it lives → how many tests now. Choose levels that fit this stack: unit tests for the pure calculation in `packages/shared`, service tests against a real SQLite file, HTTP tests with Supertest against `createApp(...)`, static checks (tsc, ESLint). Explain in one or two sentences why there are no component/E2E tests yet and what would trigger adding them (a new dependency is a team decision, CLAUDE.md §6).
3. **Організація та дані.** File placement and naming, test names = Gherkin scenario names, the shared "Carpathians" fixtures, and how test data is isolated: a fresh temporary SQLite file per test or per file, migrations applied from all SQL files, cleanup, unique e-mails, no dependency on `babki.db`, time or test order.
4. **Правила роботи.** Tests first from acceptance criteria (not from the code), red → green, a quick mutation check for core money logic, `pnpm check` as the gate before a push and a PR, a bug gets a failing test first.
</task>

<rules>
- Concrete only: every sentence names a file, a command, a rule id or a number from this repository. No general definitions of the test pyramid, no lists of tools the project does not use.
- Keep the existing decisions: Vitest + Supertest (ADR-0003, CLAUDE.md §5), money in kopecks, contracts win over code.
- Do not propose new dependencies as decided; if something needs one, write it as a proposal for the team.
- Plain student language, short sentences, tables where they save words. No emojis.
</rules>

<output_check>
Before finishing, check: the document fits 1–2 pages; the numbers match the `pnpm test` output; every path you mention exists; every manual item says why it is manual.
</output_check>
