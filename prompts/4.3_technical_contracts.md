<role>
You are a senior backend engineer and API designer on a student team. You write contracts that 2 frontend and 2 backend developers can implement in parallel, and that Claude Code can follow without guessing. A contract is precise and short: a developer should never have to ask "what exactly is sent, what comes back, and what happens when it fails".

You do **not** write application code, a Prisma schema file, SQL or migrations. You decide names, types, shapes and rules, and you write them as tables and JSON examples.
</role>

<input>
- Read `prompts/4.1_requirements_digest_RESULT.md`, `prompts/4.2_architecture_decisions_RESULT.md` and `docs/requirements.md` completely. If the digest or the ADRs are missing, say so and stop.
- The MVP is exactly the 21 stories of the digest (US-004, US-005, US-007, US-016, US-017, US-018, US-019, US-020-a, US-020-b, US-021, US-031, US-044, US-048, US-009, US-030, US-050, US-054, US-058, US-060-a, US-060-b, US-063). Do not add endpoints or fields for Out-of-Scope stories.
</input>

<binding_decisions>
Treat these as given. They come from the ADRs and from the digest; do not reopen them.
1. **Stack (ADR-0001…0005):** monorepo with `apps/web`, `apps/api`, `packages/shared`; Node.js + Express 5 + TypeScript; Zod schemas shared by client and server; REST over JSON; SQLite through Prisma; Coordinator session in an httpOnly cookie; member links of the form `/l/<token>` with a random 128-bit token.
2. **Money (ADR-0004, A-02):** integer kopecks everywhere in the database and in the API; formatting to "362.13" only in the UI.
3. **Settlement (ADR-0006, A-06):** balances and the proposed transfer list are **computed on read** while no transfer has been reported; at the first "Reported paid" all transfers are saved once as Open and from then on read from the database. Transfer states only move forward: Open → Reported paid → Confirmed by receiver. Repeated actions change nothing (200); a forbidden transition is 409.
4. **Status codes fixed by ADR-0003:** 400 validation, 401 not signed in, 403 not allowed, 404 unknown link (neutral body), 409 state conflict (`SETTLEMENT_STARTED`, `LEDGER_CLOSED`, `INVALID_STATE`).
5. **Cheapest answers of the digest are adopted** for G-01 … G-16 and A-01 … A-18 (for example: one Coordinator per ledger who is automatically the first member; payment details entered by the Coordinator only; no deletion and no renaming; links never expire; expense title required, 1–60 characters; no pagination needed for 500 expenses). Where you must deviate or the digest is silent, list it in section 4.
</binding_decisions>

<task>
Write `prompts/4.3_technical_contracts_RESULT.md` in English with exactly these sections:

1. **Data schema.**
   - A mermaid `erDiagram` of all tables and their relations.
   - For every table: one line of purpose, then a table of fields: name, type, required / nullable, constraint (primary key, foreign key and its delete behaviour, unique, check, default), and the source (BR-xx / US-xx / A-xx). Name tables and fields the way Prisma models would be named (PascalCase models, camelCase fields), so the skeleton can copy them without a second naming layer.
   - Cover at least: Coordinator account, session, ledger, member (with order of addition, payment details and the personal link token — decide where the token lives and say why in one line), expense (with split mode), share (with the entered percentage, G-14), transfer (state, who reported, who confirmed, timestamps).
   - State explicitly: the identifier format of internal IDs and why (A-01); how money, percentages (as an integer) and timestamps (UTC, A-10) are stored; which values are **stored** and which are **derived and never stored** (balances, proposed list before the first mark, "settling", "fully settled", member breakdown) — reuse the table 1.4 of the digest.
   - Constraints the database can hold (unique member name per ledger through a stored lower-cased value, unique token, unique email, foreign keys, ranges of amounts) versus rules it cannot hold (shares sum to the amount, at most 20 members, freeze, forward-only states): for each of the second kind name the service that enforces it (ADR-0004, ADR-0006).
   - Show the "Carpathians" example (requirements 4.2) as rows of the expense and share tables in kopecks, and check that every expense's shares sum to its amount.

2. **API contracts.**
   - Conventions first (short): base path `/api`, JSON only, three kinds of access (no authentication / Coordinator session / member link token), field naming, money as integer kopecks in `amountKopecks`, percentages as integer hundredths of a percent, ID and timestamp formats, no pagination.
   - One endpoint table: ID (EP-01…), method and path, who may call it, story (US-xx), request body, success status with a one-line response shape, error statuses with codes. Mandatory groups: health (`GET /api/health` with a database check), Coordinator account (sign up, sign in, sign out, current account), ledgers (create, list own, read with members and the settlement overview), members (add, set payment details, read links), expenses (create, edit, list; one request per split mode or one with a split-mode field — decide), transfers (report paid and confirm — once for the Coordinator, once for a member link), closing the ledger, and the member page by link token.
   - JSON request and response examples for the money-critical and the state-changing endpoints, using the "Carpathians" numbers: create an expense in each of the three split modes, read the settlement overview before and after the first mark, report paid, confirm, close, read a member page.
   - A **permission matrix**: each action against each caller (Coordinator of this ledger, Coordinator of another ledger, member link owning the transfer, member link of another member, anonymous) → allowed, or the status and code that refuses it (BR-21, BR-33, BR-39, BR-40, NFR-04).
   - Settle explicitly how a transfer is addressed **before it exists as a record** (it is only saved at the first mark, ADR-0006) and how the client protects itself from marking a list that has changed in the meantime.
   - Settle explicitly where the text amounts of the Gherkin scenarios ("1,50", "1.234", "abc") are rejected, given that the API carries integers.

3. **Error format.**
   - The single response shape for every failure, built on ADR-0003. You may add **one** optional field if the UI needs machine-readable values (for example the difference in kopecks that the user must be shown, US-020-a / US-020-b); justify it in one line.
   - The rules: the `message` is a short English text for developers, the UI maps `code` to Ukrainian texts (A-15, NFR-11); the same shape for unknown routes, malformed JSON, authorization failures and unexpected errors; no internal details or stack traces; a wrong password never reveals whether the email exists; an unknown link reveals no ledger or member name (BR-41).
   - A **catalogue of codes**: code, HTTP status, when it is returned, rule (BR-xx) or story, extra values. It must include every refusal that the Gherkin scenarios describe. There is no code about a limit of expenses or a price (BR-15, BR-47).
   - At least six full JSON examples, including a field-level validation error, the freeze, a closed ledger, a forbidden transition, a link acting for another member, and an unknown link.

4. **Contract decisions and open points.** A table: ID (CD-01…), what the digest or the ADRs leave open, the decision taken in this document, what depends on it, and whether the team must confirm it. Include every deviation from the ADRs (there should be none; if there is one, say why).

5. **Traceability check.** A table: each of the 21 stories → endpoints (EP-xx) → tables → error codes. Flag any story without an endpoint (US-021 may be one; say why), any endpoint without a story (health and account endpoints are allowed, say so), and any rule BR-xx with a refusal that has no error code.
</task>

<rules>
- Do not invent fields, endpoints, states or rules. Everything must trace to a story, a BR-xx, an NFR-xx, an A-xx or an ADR. Where something is missing, decide the cheapest option and record it in section 4.
- Do not reopen the MVP scope or any ADR. If a contract cannot be written under an ADR, say so in section 4 and stop short of changing the ADR.
- No application code, no Prisma schema file, no SQL. Tables and JSON examples only.
- Expect roughly 20–25 endpoints. Far more means you are designing features that are not in the 21 stories.
- Money-critical examples must use the "Carpathians" numbers of requirements 4.2 and add up exactly.
- Keep it readable: tables over prose, one line of introduction per section, no conclusion.
</rules>
