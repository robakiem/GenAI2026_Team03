# Prompt 4.5: Walking Skeleton (scaffold with all layers connected, no business logic)

<role>
You are a senior full-stack engineer who sets up a repository for a student team of 6 (2 frontend, 2 backend + database, 1 UI/UX, 1 AI/testing) that starts coding tomorrow. You build the **skeleton only**: structure, tooling and one working line through all three layers. Every later feature will be added by the team on top of what you create, mostly with Claude Code, so the structure must be predictable and every command must work on macOS and Windows.
</role>

<input>
- Read `prompts/4.2_architecture_decisions_RESULT.md`, `prompts/4.3_technical_contracts_RESULT.md`, `docs/requirements.md` and `README.md`. If the ADRs or the contracts are missing, say so and stop.
- The repository currently contains only `README.md`, `docs/` and `prompts/`. Do not change anything in `docs/` or `prompts/`.
</input>

<binding_decisions>
Treat these as given.
1. **Structure (ADR-0001):** one repository, pnpm workspaces: `apps/web`, `apps/api`, `packages/shared`. Backend layers `routes → services → data`; frontend `pages → feature components → API client`. Root scripts `dev`, `test`, `typecheck`.
2. **UI (ADR-0002):** React + TypeScript + Vite, React Router, TanStack Query, Tailwind CSS, mobile-first at 360 px, Ukrainian texts in one dictionary file.
3. **Backend (ADR-0003):** Node.js + Express 5 + TypeScript, `tsx` in development, Zod, Vitest + Supertest. Every error uses the single error format of the contracts.
4. **Data (ADR-0004):** SQLite through Prisma; the database is one local file that is git-ignored; money is integer kopecks.
5. **Contracts (4.3):** the Prisma schema is a literal copy of the schema section of the contracts: same models, fields, types and constraints. The health endpoint and the error format are exactly as in the contracts.
6. **Versions:** use the current stable release of every tool and library that installs cleanly, and pin exact versions. Verify them against the package registry; do not rely on memory. Follow the library's own current documentation, in particular for Prisma with SQLite (newer major versions may need a driver adapter and a configuration file).
</binding_decisions>

<task>
Create the following, in this order.

1. **Workspace (repository root).** `package.json` with the scripts below, `pnpm-workspace.yaml`, a shared `tsconfig.base.json`, `.gitignore` (dependencies, build output, the database file, `.env`), `.nvmrc` and `engines` for Node 24, `.env.example` only if some variable is genuinely needed. The project must start **without copying any file**: defaults live in code or in the Prisma configuration.
   Scripts: `dev` (applies pending migrations, then starts API and web together), `test`, `typecheck`, `build`, `db:migrate`. Scripts must work in Windows shells too: no Unix-only syntax.

2. **`packages/shared`.** Only what the contracts already define: the error-response schema and type, the list of error codes, the health-response schema and type. Exported as TypeScript with Zod. **No calculation, no money helpers, no validation of business input.**

3. **`apps/api`.** Layered folders `routes`, `services`, `data` (plus the app entry and a configuration file). Implemented: `GET /api/health` returning 200 and the body defined in the contracts after a real `SELECT 1` through Prisma; the same endpoint answers with the contract's error code and status when the database is not reachable; JSON body parsing; a 404 handler and a final error handler that produce the unified error format (including for malformed JSON and unexpected errors, without a stack trace in the body). One Vitest + Supertest test for the health endpoint and one for the 404 format. Layers that have nothing to hold yet contain a short `README.md` or a placeholder file saying what belongs there, not code.

4. **Data layer.** `apps/api/prisma/schema.prisma` copied from the contracts, the initial migration generated from it, a single Prisma client module in `data`. No seed script, no queries other than the health check.

5. **`apps/web`.** React + Vite + TypeScript with Tailwind, Router and TanStack Query configured; a Vite dev proxy for `/api` (same site, so the cookie of ADR-0005 will work later); the Ukrainian dictionary file. Routes as placeholder pages that show only the screen name in Ukrainian: sign up, sign in, my trips, create trip, trip overview, add expense, edit expense, proposed transfers and payment overview, the member page `/l/:token`, and "link not found" for any unknown address. Take the paths from the contracts where they define them. The start page shows the project name **Babki**, one line about what it is, the list of future screens as links, and a status line that calls `/api/health` through the API client and shows "API: ok · DB: ok" or a readable error. The layout must be usable at 360 px without horizontal scroll. No sign-in guard, no forms, no business texts beyond the screen names.

6. **Launch and documentation.** Add one section "Як запустити" (Ukrainian, like the rest of the README) to `README.md` with: the prerequisites (Node 24 and how to get pnpm if it is missing, for example through Corepack), the one or two commands that start everything (`pnpm install`, then `pnpm dev`), the addresses of the web page and of the health endpoint, how to run the tests and the type check, and where the database file is. Do not rewrite other parts of the README.

7. **Verify and report.** On a clean copy of the repository (without `node_modules` and without the database file) run exactly the commands of the README. Then show: the output of `GET /api/health`; the same endpoint with the database unavailable; `pnpm typecheck`; `pnpm test`; `pnpm build`; and a screenshot of the start page at 360 px width showing the status line. State plainly what you could **not** verify (for example Windows).
</task>

<out_of_scope>
Do not create or install anything that the skeleton does not use. In particular no: authentication, argon2 or sessions, any endpoint besides health, any service logic, share or balance or transfer calculation, seed data, forms, state management beyond TanStack Query, Docker, CI configuration, deployment files, linters or formatters beyond what the template ships with, `CLAUDE.md` or other AI-assistant files (a separate task), changes to `docs/` or `prompts/`.
</out_of_scope>

<rules>
- Do not invent fields, tables or endpoints. If the contracts are wrong or incomplete for the skeleton, stop and report what is missing instead of silently changing the schema; if a correction is obviously needed, make it in the contracts file too and say so.
- Minimal code: every file must be needed by one of the points above. No example features, no commented-out code, no TODO lists in code.
- Comments only where the reason is not obvious, in English. Texts for the user are Ukrainian and live only in the dictionary file.
- Do not commit. Leave the working tree for review.
</rules>

<definition_of_done>
- `pnpm install` and `pnpm dev` on a clean copy start the API and the web page with no further steps.
- The start page opens in the browser and shows "API: ok · DB: ok".
- `GET /api/health` returns 200; with the database unavailable it returns the contract's error in the unified format.
- The database file is created by the initial migration and contains exactly the tables of the contracts.
- `pnpm typecheck`, `pnpm test` and `pnpm build` pass.
- `git status` shows only the new skeleton files and the README change.
</definition_of_done>
