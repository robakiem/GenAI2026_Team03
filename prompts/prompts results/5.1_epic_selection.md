# Rationale for the Chosen End-to-End Scenario

## Selected epic

For this iteration we implement a single, logically complete epic: **"Create a trip"** — the
first step of the Babki user journey (*Ledger created*). The scenario is:

> A Coordinator registers an account, creates a named trip ledger, adds friends to it without
> requiring them to register, and then views the trip together with its list of members and
> their personal links.

It corresponds to user stories **US-004** (*Create a ledger*) and **US-005** (*Add friends
without accounts*), together with the Coordinator account that creating a ledger presupposes
(sign-up, sign-in, sign-out), as established by contract decision **CD-02**.

## Why this scenario

**1. It is a complete, self-contained user journey.** The scenario can be traversed from
beginning to end without any missing prerequisite: a brand-new user signs up, creates a trip,
populates it with members, and sees the persisted result. It matches the assignment's reference
pattern — *"creating an entity and displaying it in a list."* No part of the flow depends on
functionality that is deferred to a later iteration.

**2. It is the correct first slice architecturally.** Every other story in the MVP — recording
expenses, computing balances, settling transfers, the member-facing link page — depends on a
Coordinator account, an existing ledger, and its members. This epic establishes that foundation
(authentication, session management, ledger and member creation). Implementing it first removes a
hard dependency for all subsequent work, whereas any other slice would require this one to already
exist.

**3. It exercises all application layers.** The scenario is genuinely vertical and touches every
tier of the architecture:

- **UI** — sign-up / sign-in forms, a "create trip" form, an "add member" form, and a trip
  overview screen (React + Vite, Ukrainian interface, mobile-first).
- **Business logic** — input validation (name and e-mail limits, uniqueness), business rules
  (one Coordinator per ledger, case-insensitive unique member names, the 20-member limit, ordered
  positions), password hashing, session handling, and ownership-based access control, isolated in
  the service layer.
- **Persistence** — real reads and writes to the `Account`, `Session`, `Ledger`, and `Member`
  tables through Prisma over a file-based SQLite database.

**4. It satisfies the persistence requirement convincingly.** The data is written to an on-disk
SQLite file (`babki.db`), not to volatile memory. The created account, trip, and members survive
an application restart, and the "sign out → sign in → the trip is still listed" flow demonstrates
reading the data back from storage. This directly fulfils the requirements that *data must be
really saved to the database* and *must not disappear after the program restarts*.

**5. It deliberately avoids the "code everything at once" trap.** The scope intentionally excludes
the project's most complex and error-prone components — the deterministic settlement algorithm, the
forward-only transfer state machine, money-splitting arithmetic, and the member-facing pages. Those
are reserved for subsequent slices. Keeping this first iteration narrow protects correctness and
keeps the diff small enough for a meaningful AI code review.

## Scope summary

| Dimension | In scope |
|---|---|
| User stories | US-004, US-005 (+ Coordinator account, CD-02) |
| Endpoints | EP-02 … EP-09 (authentication, ledgers, members) |
| Tables | Account, Session, Ledger, Member |
| Screens | `/signup`, `/signin`, `/ledgers`, `/ledgers/new`, `/ledgers/:ledgerId` |

**Explicitly out of scope** (deferred to later iterations): expenses and shares, settlement and
transfers, the settlement algorithm, the member link page (`/l/:token`), payment-details editing,
payment reporting / confirmation, and trip closing.

## Acceptance

The slice is considered complete when the deterministic checks (`pnpm typecheck`, `pnpm test`,
`pnpm build`) pass, the US-004 and US-005 acceptance criteria and Gherkin scenarios are covered by
tests, and the full journey can be demonstrated live on persisted data:

> sign up → create "Carpathians" → add Max, Iryna and Andrii → view the trip with four members →
> restart the server → the data is still there.
