# Babki — Architecture Decision Records

Built on `4.1_requirements_digest_RESULT.md` (rules BR-xx, assumptions A-xx, gaps G-xx). All ADRs are **Proposed**; the team switches them to Accepted after review.

**Constraints used for every rating:** 6 students (2 frontend, 2 backend + DB, 1 UI/UX, 1 AI/testing); everyone knows TypeScript, React, Node.js; backend developers also know Express, .NET, Python, Java; no DevOps experience; 7 weeks to the demo; 0 UAH; one-command local launch on macOS and Windows; most code written with Claude Code; money is involved, so correctness beats features.

**Demo assumption:** the demo runs locally. Free hosting is optional; ADR-0004 states what changes if it becomes required.

| ADR | Decision | Status |
|---|---|---|
| 0001 | Monorepo (pnpm workspaces: `web`, `api`, `shared`), layered modular monolith | Proposed |
| 0002 | Web SPA: React + Vite, React Router, TanStack Query, Tailwind CSS | Proposed |
| 0003 | Node.js + Express 5 + TypeScript, Zod validation, REST/JSON, Vitest | Proposed |
| 0004 | Relational DB: SQLite via Prisma; money as integer kopecks | Proposed |
| 0005 | Email + password with server-side sessions in an httpOnly cookie; random 128-bit link tokens | Proposed |
| 0006 | Balances and transfers computed on read by a pure function; transfers saved once at the first "Reported paid"; guarded state updates in transactions, 409 on conflict | Proposed |

Ratings: **+** fits our constraints · **0** neutral · **−** works against them.

## ADR-0001: Repository structure and architecture style

**Status:** Proposed

**Context.** Frontend and backend must share money rules and validation (BR-01…BR-09, BR-16, BR-19), otherwise the same check is written twice and drifts. A-02 (kopecks) and BR-23 (determinism) must be one implementation. One-command launch; 6 people working in parallel; Claude Code needs a predictable layout.

**Options**

| Criterion | A. Monorepo `web` + `api` + `shared` | B. Two repositories | C. One Next.js full-stack app |
|---|---|---|---|
| Shared types and rules | + one `shared` package | − copy or publish a package | + one codebase |
| Team knowledge | + plain React + Express | + | 0 Next.js server parts are new to most |
| Parallel work of 2 FE + 2 BE | + clear folders | + | 0 front and back in one tree |
| One-command launch | + one root script | − two clones, two starts | + |
| Predictability for Claude Code | + explicit boundaries | 0 | 0 mixed client/server code |

**Decision.** **A**: one repository with pnpm workspaces — `apps/web`, `apps/api`, `packages/shared`. Backend is a **layered modular monolith**: `routes → services → data`, business rules only in services and `shared`, never in routes or React components. Frontend: pages → feature components → API client. Root scripts `dev`, `test`, `typecheck` run all packages.
Main criterion: one implementation of money rules for UI and API. Would change if the frontend and backend teams had to deploy independently.

**Consequences.** Simpler: one clone, one install, shared Zod schemas and types, one PR touches both sides of a story. Harder: everyone needs pnpm; workspace configuration once at the start. Postponed: microservices — not needed for 20 members and 500 expenses (NFR-12). Accepted risk: a broken `shared` package breaks both apps; mitigated by `typecheck` in every run.

**Related.** All stories; BR-01…BR-09, BR-23; NFR-05, NFR-06.

## ADR-0002: UI stack

**Status:** Proposed

**Context.** Friends open a link on a phone without installing anything (US-007, US-009, NFR-10); 360 px width; Ukrainian interface (NFR-11, G-15). The Coordinator works on a phone during the trip. The UI must never show stale transfers (BR-26, NFR-09).

**Options**

| Criterion | A. React SPA + Vite | B. Next.js | C. React Native (mobile app) |
|---|---|---|---|
| "No installation" for friends | + | + | − needs installation or a separate web build |
| Team knowledge | + | 0 SSR, server components | 0 new tooling, emulators |
| Effort in 7 weeks | + | 0 | − two platforms to test |
| Fits ADR-0001 (separate `api`) | + | 0 duplicates the server role | 0 |
| SEO / server rendering | 0 not needed: pages are private | + not needed | − |

**Decision.** **A**: web SPA — React 19 + TypeScript + Vite; React Router for pages (Coordinator pages behind sign-in, member page `/l/:token`); TanStack Query for server data, with every mutation invalidating balances and transfers so nothing stale is shown (BR-26); Tailwind CSS, mobile-first at 360 px; Ukrainian texts in one dictionary file keyed by the message identifiers from the Gherkin scenarios (A-15).
Main criterion: a friend opens a link in any mobile browser with no install. Would change if the product needed offline mode or push notifications (both out of scope).

**Consequences.** Simpler: one platform to test, the UI/UX designer's screens map to pages directly. Harder: client-side routing needs a fallback route on the dev server and on any host. Postponed: PWA/offline (US-023 out of scope), dark theme.

**Related.** US-009, US-030, US-044, US-048, US-050, US-060-a, US-060-b; BR-26, BR-40, BR-47; NFR-10, NFR-11.

## ADR-0003: Backend stack

**Status:** Proposed

**Context.** The API enforces every permission and state rule (BR-29…BR-36, BR-39); validation must match the frontend exactly (BR-13); single error format; tests must reproduce Gherkin scenarios. Backend developers know Express, .NET, Python and Java; everyone knows TypeScript.

**Options**

| Criterion | A. Node + Express 5 | B. Node + NestJS (or Fastify) | C. .NET (ASP.NET Core) |
|---|---|---|---|
| Shared types/validation with `web` | + same Zod schemas | + | − rewrite rules in C#, keep in sync manually |
| Team knowledge | + both backend devs know Express | 0 NestJS concepts new to most | 0 backend only; frontend devs cannot help |
| Effort in 7 weeks | + minimal framework | 0 more structure to learn | 0 |
| Strong typing and correctness | 0 TS types + Zod at runtime | + | + |
| Fit with one-command launch | + | + | 0 second runtime to install |

**Decision.** **A**: Node.js 24 LTS + Express 5 + TypeScript (run with `tsx` in development). Validation by **Zod** schemas from `packages/shared`, used both in forms and in API middleware. REST over JSON. One error shape for every failure:
`{ "error": { "code": "VALIDATION_ERROR", "message": "...", "details": [{ "field": "...", "message": "..." }] } }` with status codes 400 validation, 401 not signed in, 403 not allowed (e.g. a link acting for another member, BR-33), 404 unknown link (neutral body, BR-41), 409 state conflict (freeze, ADR-0006). Tests: **Vitest** for services and `shared`, **Supertest** for HTTP; test names carry the Gherkin scenario name.
Main criterion: one language and one set of validation rules from form to database. Would change to .NET if the team decided to keep the frontend and backend codebases fully separate.

**Consequences.** Simpler: frontend developers can read and fix backend code; Claude Code works in one language. Harder: Express gives little structure, so the layering from ADR-0001 must be kept by convention and review. Postponed: OpenAPI generation, rate limiting (only relevant once hosted).

**Related.** All stories; BR-13, BR-29…BR-39, BR-41; NFR-02, NFR-07.

## ADR-0004: Data storage

**Status:** Proposed

**Context.** Data is strongly relational (Ledger → Members → Expenses → Shares; Transfers between Members) with invariants that must hold atomically: an expense and its shares saved together or not at all (BR-13, NFR-07), forward-only transfer states (BR-31). Exact money (NFR-06). Volume is small: 20 members, 500 expenses (NFR-12). One-command local launch, no DevOps, 0 UAH.

**Options**

| Criterion | A. SQLite + Prisma | B. PostgreSQL + Prisma | C. MongoDB |
|---|---|---|---|
| Relational data, transactions | + | + | 0 multi-document transactions are extra work |
| One-command local launch | + a file, nothing to install | − local install or Docker | − local install or a cloud account |
| Free demo hosting | − file is lost on most free hosts | + free managed tiers | + free tier |
| Team knowledge | + | + | 0 |
| Concurrency for our scale | + single writer serialises writes | + | 0 |

**Money.** Integer kopecks (`Int`) in every table and in all arithmetic; formatting to "362.13" only in the UI (A-02). Decimal types are rejected: they push rounding into the database and the language runtime and make BR-02 harder to prove.

**Decision.** **A**: SQLite through **Prisma** (schema, migrations, typed client); `pnpm db:migrate` creates the local database; a seed script loads the "Carpathians" example (requirements 4.2). Every amount is an integer number of kopecks. Constraints the schema can hold: unique member name per ledger (stored lower-cased, BR-19), unique link token, foreign keys. Rules the schema cannot hold (shares sum to the amount, ≤ 20 members, freeze, forward-only states) live in services inside transactions (ADR-0006).
Main criterion: zero setup for six laptops. Would change if the demo must run on a free host — then switch the Prisma provider to PostgreSQL on a free managed tier; the services do not change, migrations are regenerated once.

**Consequences.** Simpler: `git clone` → `pnpm install` → `pnpm db:migrate` → `pnpm dev`. Harder: SQLite and PostgreSQL differ in case-insensitive comparison and locking, so name uniqueness uses a stored lower-cased column instead of database collation. Accepted risk: the demo depends on one laptop's database file.

**Related.** US-004, US-005, US-016…US-021, US-031; BR-02, BR-13, BR-19, BR-20; NFR-06, NFR-07, NFR-12.

## ADR-0005: Authentication and access

**Status:** Proposed

**Context.** Team decision: the Coordinator signs in with email + password; friends never register and act through a personal link (BR-38). Links must be unguessable and must not expose internal IDs (NFR-01, A-01). MVP account scope: sign up, sign in, sign out; no email verification and no reset (G-03, A-08). The Coordinator stays signed in during a trip (A-09). Two kinds of actor, two kinds of permission check (BR-21, BR-33, BR-39).

**Options**

| Criterion | A. Server session + httpOnly cookie | B. JWT in localStorage | C. External auth service (free tier) |
|---|---|---|---|
| Security for a student team | + cookie not readable by scripts; sign-out really ends the session | − token readable by any injected script; sign-out cannot revoke | + |
| Effort | + one sessions table and a middleware | 0 | 0 account, keys, callback setup |
| Works offline / locally | + | + | − needs internet and an external account |
| 0 UAH, no external dependency | + | + | 0 free tier limits |

**Decision.** **A**.
- **Coordinator:** passwords hashed with **argon2id** (bcrypt acceptable if argon2 does not install on a Windows laptop); minimum 8 characters; email stored lower-cased and unique. On sign-in the API creates a session row with a random ID and sends it in an `httpOnly`, `SameSite=Lax` cookie; session lifetime 30 days, extended on use. Every Coordinator route checks the session and that the ledger belongs to that account (NFR-04).
- **Member links:** a random token of 128 bits (22 base64url characters) generated with a cryptographic generator, stored unique, never derived from IDs; URL `/l/<token>`. The token resolves to exactly one member and allows only: read own page, mark own outgoing transfer, confirm own incoming transfer (BR-33, BR-38…BR-40). Unknown token → 404 with a neutral body (BR-41).
Main criterion: the simplest scheme that is still safe for financial data. Would change if password reset became mandatory — then an email-sending service is needed.

**Consequences.** Simpler: no external services; two small middlewares (`requireCoordinator`, `requireMemberLink`). Harder: frontend and API must run on the same site so the cookie is sent (Vite dev proxy). Accepted risks: forgotten password = lost access to own ledgers (A-08); a forwarded link exposes one member's data with no revocation (A-13).

**Related.** US-004, US-005, US-007, US-009, US-054, US-058, US-063; BR-21, BR-33, BR-38…BR-41; NFR-01…NFR-04.

## ADR-0006: Settlement calculation and consistency

**Status:** Proposed

**Context.** Balances and the transfer list are derived and must never be stale (BR-26, NFR-09); the list must be identical for the same expenses in any order (BR-23, NFR-05) and equal the "Carpathians" result. Transfers also carry state that must persist (G-01). After the first "Reported paid" expenses are frozen (BR-36); states only move forward (BR-31); repeated actions change nothing (BR-34). Coordinator and friends act from different devices at the same time (NFR-08).

**Options**

| Criterion | A. Compute on read + save transfers at first mark | B. Store balances and transfers, update on every change | C. Always compute, keep states in a separate table keyed by (from, to) |
|---|---|---|---|
| Never stale (BR-26) | + nothing to keep in sync | − every write must update derived data correctly | + |
| Determinism and testability | + one pure function | 0 depends on update order | + |
| Persistent states (G-01) | + saved once, frozen afterwards | + | 0 states may detach if amounts change |
| Effort | + | − | 0 |
| Performance at 500 expenses | + trivial | + | + |

**Decision.** **A**.
- **Calculation.** A pure function in `packages/shared`: input = members in ledger order + expenses with shares (kopecks), output = balances and the proposed transfer list. Algorithm: greedy matching of the largest debtor with the largest creditor; ties broken by ledger order of members (A-16, G-08). Share splitting (equal, amounts, percentages) is another pure function with the BR-05/BR-09 kopeck rules. Both run on every read while the ledger is Active.
- **First mark.** "Reported paid" on a ledger with no saved transfers runs in one transaction: compute the list → insert all transfers as Open → move the chosen one to Reported paid. From then on transfers are read from the database and never recalculated (A-06).
- **Guarded updates.** Every state change is a conditional update: `UPDATE transfer SET state = 'REPORTED_PAID' WHERE id = ? AND state = 'OPEN'`. Zero rows changed because it is already in the target state → 200, no change (BR-34). Zero rows because the transition is not allowed (e.g. confirm while Open) → 409 `INVALID_STATE`.
- **Freeze.** Adding or editing an expense checks, in the same transaction as the write, that no saved transfers exist and the ledger is not Closed; otherwise 409 `SETTLEMENT_STARTED` / `LEDGER_CLOSED` (BR-36, BR-44). With SQLite's single writer the edit and the first mark are serialised, so exactly one of them wins (NFR-08).
- **Tests.** The "Carpathians" data and every Gherkin example table become Vitest cases on the pure functions (names = scenario names); one test shuffles expense order and compares lists (BR-23); one test fires an edit and a mark in parallel and expects one 409.
Main criterion: correctness of money with the least code that can go wrong. Would change if edits after "paid" were allowed (G-07) — then option C with re-matching rules.

**Consequences.** Simpler: no derived data to keep in sync; the core logic is testable without a database or HTTP. Harder: the first mark is a special case and must be covered by tests. Accepted risk: a mistaken "Reported paid" freezes the ledger with no undo (G-07).

**Related.** US-019, US-020-a, US-020-b, US-031, US-044, US-048, US-054, US-058, US-060-a, US-060-b, US-063; BR-02…BR-09, BR-23…BR-37, BR-44, BR-46; NFR-05, NFR-06, NFR-08, NFR-09.
