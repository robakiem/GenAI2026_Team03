<role>
You are a pragmatic tech lead for a student team. You choose what this team can actually build and demo, not what a large company would build. You compare options honestly against the constraints below, and you write short ADRs that a teammate reads in two minutes.
</role>

<input>
- Read `prompts/4.1_requirements_digest_RESULT.md` (entities, rules BR-xx, non-functional requirements, gaps, assumptions A-xx) and `docs/requirements.md`.
- If the digest is missing, say so and stop: decisions must be built on it.
- Gaps from the digest that are marked "must answer before architecture" and that you cannot settle from the constraints below — ask me in Plan Mode, do not guess.
</input>

<team_constraints>
These matter more than "best practices".
- **Product:** Babki, a mobile-friendly web service for splitting a trip's shared expenses. One active user role with an account (Coordinator, **email + password** — team decision), all other people act through personal unguessable links without registration. Small data: test volume 500 expenses and 20 members per ledger.
- **Team:** 6 students — 2 frontend, 2 backend + database, 1 UI/UX designer, 1 AI-logic/testing. Everyone knows TypeScript, React and Node.js. The backend developers also know Express, .NET, Python and Java. No DevOps experience.
- **Deadline:** 7 weeks to the demo, in parallel with other courses.
- **Budget:** 0 UAH — free tiers only.
- **Launch:** locally with one command after `git clone`, on macOS and Windows laptops; the demo may also be shown from a free hosting.
- **Way of working:** most code will be written with Claude Code, so a predictable structure, one language where possible, and types shared between frontend and backend matter.
- **Correctness over features:** money is involved; a rounding or state error costs more than a missing feature.
</team_constraints>

<decisions_to_make>
Exactly **six ADRs**, one per decision. Fold every smaller question into the ADR it belongs to instead of opening a new one.
1. **Repository structure and architecture style** — monorepo vs separate repos; how frontend, backend and shared code are split; backend style (layered / modular monolith / clean-hexagonal / microservices) and frontend structure; how the app is launched locally with one command.
2. **UI stack** — web vs mobile app (based on the user journey: friends open a link on a phone); build tool, routing, server-state handling, styling, Ukrainian texts.
3. **Backend stack** — language and framework (compare at least Node/Express, another Node framework, and one of .NET / Python / Java that the team knows), validation, API style, single error format, test runner.
4. **Data storage** — relational vs document; database for local run and for free demo hosting; ORM / query layer and migrations; **money representation** (e.g. integer kopecks vs decimal).
5. **Authentication and access** — Coordinator email + password: password hashing, session vs token, where it is kept on the client, password reset in the MVP or not; **personal member links**: token format and length, how a token maps to one member and to the allowed actions only.
6. **Settlement and consistency** — store or recalculate balances and the transfer list; how determinism ("same expenses in any order → same list") is guaranteed and tested on the "Carpathians" example; how the freeze after the first "Reported paid", forward-only transfer states and idempotent repeated actions hold when two requests arrive at once; HTTP status for conflicts.
</decisions_to_make>

<process>
**Step 1 — Plan (Plan Mode, write nothing).** For each of the six decisions: the order they must be taken in (what depends on what), 2–3 realistic options, and which digest gaps it depends on. Ask me anything you lack. Wait for my approval.

**Step 2 — after approval, write one document `prompts/4.2_architecture_decisions_RESULT.md`** with a short index table (ADR, decision, status) and then the six ADRs (0001–0006), each in this format:
```
# ADR-NNNN: Title
Status: Proposed
Context — constraints and digest items (BR-xx, A-xx, gaps) that force the decision
Options — a table of 2–3 options rated against OUR constraints (+ / 0 / −): team knowledge, 7-week effort, 0 budget, one-command local run, shared types, correctness for money
Decision — what we choose, the main criterion that tipped it, and what would have to change for a different choice
Consequences — what becomes simpler, what becomes harder, what we postpone, which risk we accept
Related — stories (US-xx) and rules (BR-xx)
```
The team switches the status to Accepted after review.
</process>

<rules>
- Every rating must be justified by a constraint, a digest item or a story, not by popularity.
- Respect the binding decisions in the digest (email + password, personal links, deterministic algorithm, no money transfer). Do not reopen the MVP scope.
- Concrete names and versions are expected here (frameworks, database, libraries), but no application code and no schema files — only decisions.
- Concise: ADRs are read, not studied. No ADR longer than one screen.
</rules>
