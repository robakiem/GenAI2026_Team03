# 5.2 Fixing and refactoring: deterministic checks (guardrails)

## 1. The guardrail set and the rules the AI follows

One command runs everything and stops at the first failure: `pnpm check` = `pnpm typecheck` → `pnpm lint` → `pnpm test` → `pnpm build`.

| Check | Command | What counts as success |
|---|---|---|
| Types | `pnpm typecheck` | no findings in `shared`, `api`, `web` (TypeScript `strict` plus `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns`, `noFallthroughCasesInSwitch`) |
| Linter | `pnpm lint` (`eslint .`) | 0 errors and 0 warnings (checked with `--max-warnings=0`) |
| Tests | `pnpm test` | all tests green (Vitest + Supertest, persistence on a real SQLite file) |
| Build | `pnpm build` | the web build succeeds |

The project had **no linter**, so it was added: ESLint 10.14.0, typescript-eslint 8.72.2 with the type-aware `recommendedTypeChecked` set, `@eslint/js` 10.0.1, eslint-plugin-react-hooks 7.1.1 and `globals` 17.14.0, all as exact-version dev dependencies in the root `package.json`, with the scripts `lint` and `check`. Type-aware rules are needed because the API is async Express/Prisma code and the web uses TanStack Query and React Router's promise-returning `navigate`: dropped promises and untyped `any` hide exactly there. The compiler was also made stricter in `tsconfig.base.json` (the four flags above); the code already satisfied them.

Rules for fixing:
- Silencing a finding is forbidden: `eslint-disable`, `@ts-ignore`, `@ts-expect-error` and `as any` must not be used. The cause is fixed, not the symptom.
- Behaviour, contracts, status codes, UI texts and the DB schema do not change during fixes (CLAUDE.md, section 6). `docs/` and `prompts/` are not edited by the fixes.
- Validation and types come from `packages/shared`; they are not duplicated.

Two configuration choices are the only places where the linter is not applied as-is, and both are deliberate:
1. `@typescript-eslint/no-unused-vars` ignores names starting with `_` (`argsIgnorePattern`, `varsIgnorePattern`). Express recognises an error handler only by its four arguments, so the unused `_next` must stay.
2. Type-aware rules are switched off for plain `.js` files (`eslint.config.js` itself), because they are not part of any `tsconfig`. The config file is still linted with the non-type-aware rules; it is not put into `ignores`.

The linter configuration (`eslint.config.js`, flat config at the repository root):

```js
import js from "@eslint/js";
import globals from "globals";
import reactHooks from "eslint-plugin-react-hooks";
import tseslint from "typescript-eslint";

export default tseslint.config(
  { ignores: ["**/node_modules/**", "**/dist/**", "apps/api/src/data/generated/**"] },
  js.configs.recommended,
  ...tseslint.configs.recommendedTypeChecked,
  {
    languageOptions: { parserOptions: { projectService: true, tsconfigRootDir: import.meta.dirname } },
    rules: {
      "@typescript-eslint/consistent-type-imports": "error",
      "@typescript-eslint/no-unused-vars": ["error", { argsIgnorePattern: "^_", varsIgnorePattern: "^_" }],
    },
  },
  { files: ["apps/api/**/*.ts", "packages/shared/**/*.ts"], languageOptions: { globals: globals.node } },
  {
    files: ["apps/web/**/*.{ts,tsx}"],
    languageOptions: { globals: globals.browser },
    plugins: { "react-hooks": reactHooks },
    rules: reactHooks.configs.recommended.rules,
  },
  { files: ["**/*.js"], ...tseslint.configs.disableTypeChecked },
);
```

What the rules guard against: `no-floating-promises` (a promise whose rejection is lost), `no-misused-promises` (an async function passed where a `void` callback is expected), `no-unsafe-assignment` / `no-unsafe-member-access` (`any` spreading through the code), `require-await`, `no-unnecessary-type-assertion`, `consistent-type-imports` (matches `verbatimModuleSyntax`), and the React hooks rules (`rules-of-hooks`, `set-state-in-effect`).

## 4. What the AI fixed

| Rule | Files | Fix |
|---|---|---|
| `require-await` | `apps/api/src/app.test.ts` | the fakes `async () => {}` and `async () => { throw … }` became `() => Promise.resolve()` and `() => Promise.reject(new Error(…))` |
| `no-unnecessary-type-assertion` | `apps/api/src/data/prisma-error.ts` | removed the assertion, because `"code" in error` already narrows the type |
| `no-unsafe-member-access` | `apps/api/src/errors.ts` | Express's `err` is treated as `unknown` and narrowed by a typed guard `isBodyParseError(err: unknown)` before `type` is read |
| `no-unsafe-member-access` / `no-unsafe-assignment` | `apps/api/src/http.test.ts` | supertest bodies (`any`) are parsed with the shared Zod schemas `accountResponseSchema`, `ledgerWithMembersSchema`, `errorResponseSchema`; the tests now also fail if a response stops matching the contract |
| `no-unsafe-assignment` | `apps/api/src/routes/auth.routes.ts` | `res.locals.account` is typed as the shared `Account`, the same typing `ledger.routes.ts` already uses |
| `no-floating-promises` | `apps/web/src/api/auth.ts`, `ledgers.ts`, `useAuthRedirect.ts` | `invalidateQueries(…)` and `navigate(…)` are marked with the `void` operator, because the result is intentionally not awaited (a mutation must not wait for the refetch) |
| `no-misused-promises` | `MemberRow.tsx`, `LedgerNewPage.tsx`, `LedgersPage.tsx`, `SignInPage.tsx`, `SignUpPage.tsx` | `onClick={copy}` became `onClick={() => void copy()}`, and the `onSuccess` callbacks call `void navigate(…)` |

No `eslint-disable`, `@ts-ignore` or `as any` was added.

## 5. Proof that the guardrails fail on bad code

A throw-away pair of files was added, checked and deleted: an unawaited promise, an unused parameter, `const x: number = "text"` and a `useEffect` inside an `if`.

| Command | Result |
|---|---|
| `pnpm typecheck` | exit code 1, 2 `error TS` |
| `eslint .` | 5 errors: `require-await`, `no-unused-vars`, `no-floating-promises`, `react-hooks/rules-of-hooks`, `react-hooks/set-state-in-effect` |

So compile errors, type errors and lint errors are all caught by the pipeline.
