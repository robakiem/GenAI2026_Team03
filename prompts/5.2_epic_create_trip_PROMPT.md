## Architecture & layering (hard rules)
- Dependency direction: `routes → services → data`; `web` and `api` depend on `shared`;
  `shared` depends on nothing in the repo.
- Implement in this order, tests next to the code: **shared → data → services → routes → web.**
- **shared:** the Zod request schemas **and a single `LIMITS` constant** (contracts §2.1).
  Both the web forms and the API import them — never duplicate a validation in both places.
- **data (`apps/api/src/data`):** the only layer that talks to Prisma (via `db.ts`). Thin
  repository functions; no business rules.
- **services (`apps/api/src/services`):** all BR-xx, permission/state checks, and transactions.
  Never import or touch `express` objects.
- **routes (`apps/api/src/routes`):** parse the request → call a service → send the response.
  No business rules.
- **web:** server data through TanStack Query; every mutation invalidates the affected queries
  (ledger list + ledger detail). No hard-coded user-visible strings — all in `src/i18n/uk.ts`.
  Mobile-first: every screen works at 360 px with no horizontal scroll.
- **Testability / DI:** keep `createApp(deps)` injectable, following the existing `pingDatabase`
  pattern. Extend `AppDeps` so the data layer (repositories) or the Prisma client is **injected**,
  letting Supertest run `createApp` against a test database or fakes. Do not reach for the
  singleton `prisma` inside services in a way that breaks injection.

## Critical rules for this slice (easy to get wrong)
**Account / auth** (ADR-0005; contracts §1.1–1.2; CD-15):
- Hash passwords with **argon2id** (bcrypt acceptable if argon2 won't install on Windows).
  Never store or log the raw password. Password 8–128 chars.
- Email: valid, ≤254 chars, stored **trimmed + lower-cased**, unique. Duplicate on sign-up → 409
  `EMAIL_TAKEN`.
- **Sign-up also signs the user in** (sets the cookie), then 201 `{account:{id,email}}`.
- **Sign-in:** a wrong email and a wrong password both return 401 `INVALID_CREDENTIALS` with the
  **same message** — never reveal which was wrong.
- **Session:** `id` is a random 256-bit base64url value and is the cookie value. Cookie name
  `babki_session`; `HttpOnly`, `SameSite=Lax`, `Path=/`, 30-day lifetime
  (`expiresAt = now + 30d`, moved forward on use), `Secure` only over HTTPS. Sign-out deletes the
  session and clears the cookie; it is idempotent (204 even with no session).
- **`requireCoordinator`:** resolve the session from the cookie; missing/expired → 401
  `UNAUTHENTICATED`. A ledger owned by **another** Coordinator → **404 `LEDGER_NOT_FOUND`,
  never 403** (CD-10, NFR-04).

**Ledger & member** (contracts §1.3–1.4; BR-16/17/19/20; A-05):
- **EP-06 creates the Ledger and its first Member (the Coordinator: `position 1`,
  `isCoordinator true`, its own `linkToken`) in ONE transaction.** Body `{name, coordinatorName}`;
  the account itself has no name field.
- Ledger name: trimmed, 1–60 chars, **not unique** (two ledgers may share a name and stay separate).
- Member name: trimmed, 1–40 chars; **unique per ledger ignoring case** — store `name` as typed and
  `nameKey = Unicode-lowercased(name)`; the `(ledgerId, nameKey)` unique index enforces it.
  Duplicate → 409 `MEMBER_NAME_TAKEN`.
- `position`: assigned in order of addition, 1–20; 1 is the Coordinator. The 21st member → 409
  `MEMBER_LIMIT_REACHED` (`params.limit = 20`).
- `linkToken`: generated with a **cryptographic RNG**, 22 base64url chars (128 bits), unique,
  **never derived from an id**. Every member, including the Coordinator, gets one.
- EP-08 returns members **with** `linkToken` (the UI builds `/l/<linkToken>` for sharing —
  this is the Coordinator side of US-007). EP-07 returns the account's own ledgers only.
- Keep the **defensive freeze checks** on EP-09 per the contract (adding a member when a Transfer
  row exists → `SETTLEMENT_STARTED`; on a closed ledger → `LEDGER_CLOSED`). Neither state is
  reachable in this slice, but the check keeps the service correct for later slices.

**Money & validation & errors** (CLAUDE.md §5; contracts §3):
- Money is always integer kopecks in `…Kopecks` fields — never floats, decimals or strings.
  (Barely relevant here; it governs later slices.)
- Validate every request body with a Zod schema in `shared`, driven by the single `LIMITS` table;
  the API validates with it and the forms reuse it.
- Every failure uses `{ error: { code, message, details?, params? } }`. Throw `AppError` with a
  code from `ERROR_STATUS`; the HTTP status comes from that map. `message` is short English for
  developers; the UI shows a Ukrainian text mapped from `error.code`.
- `VALIDATION_ERROR` carries `details: [{field, code, message}]` using `VALIDATION_DETAIL_CODES`.
  Empty-after-trim name → `TOO_SHORT`; over the max → `TOO_LONG`; bad email → `INVALID_EMAIL`.
- A refused request changes nothing (no partial writes): wrap multi-row writes in one Prisma
  transaction.

## UI expectations
- Ukrainian interface; all texts keyed in `src/i18n/uk.ts` (extend it; keep the message-identifier
  style). Map `error.code` → Ukrainian message there too.
- Screens:
  - `/signup`, `/signin`: email + password; on success redirect to `/ledgers`.
  - `/ledgers`: the Coordinator's trips (name + state), each linking to its overview, plus a
    "create trip" action.
  - `/ledgers/new`: `name` + `coordinatorName`; on success navigate to the new ledger.
  - `/ledgers/:ledgerId`: ledger name & state; member list (name, position, a "Координатор" badge),
    each with its shareable `/l/<linkToken>`; an add-member form (name) that appends to the list.
- TanStack Query everywhere; invalidate the ledger list and the ledger detail after create /
  add-member so a stale list is never shown. Surface field errors from `VALIDATION_ERROR.details`
  and the mapped Ukrainian text for coded errors (`EMAIL_TAKEN`, `MEMBER_NAME_TAKEN`,
  `MEMBER_LIMIT_REACHED`, `INVALID_CREDENTIALS`).
- The Vite dev proxy must forward `/api` to the API so the session cookie stays first-party
  (ADR-0005).
